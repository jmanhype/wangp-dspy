## Description
## USER INTENT
Observable outcome: first run profiles the machine, recommends a capability-safe profile, explains OOM recovery with one style-preserving remediation, shows download status, configures a bundled/local or external LLM runtime, and reaches an authorized remote host without hidden defaults.

## Context (Embedded)
- The governed repository path is plan -> durable queue -> host render -> QC gates -> assembly -> provenance/recipe; `wgp` is the stable CLI and GPU execution is never implied by planning.
- WD-cpb8 already adds the first-run capability report; this story extends that front door to actionable model/runtime/download/host readiness without duplicating doctor logic.
- A recommended profile is advisory. It must state what was measured, what was unavailable, and what still requires a separately authorized run.
- Download status is a durable state machine. It must not start a download merely by opening the product or displaying a plan.

## OUT OF SCOPE
- Unattended network downloads, paid external-provider calls, or host mutation without per-run authorization.
- Bundling weights whose licence, source, hash, and usage constraints are not recorded.

## DIFF BUDGET
Roughly 11 files, under 850 authored changed LOC, excluding downloaded assets and provider code.

## Boundary Map
PRODUCES:
- wangp/platform_profile.py -> hardware/VRAM/RAM/disk profile, recommendation, and unavailability reasons
- wangp/platform_cli.py -> first-run, profile, download, runtime, recovery, and remote-access command implementations
- predict/model_assets.py -> model download manifest/state records with source URL, hash, size, licence, and resume status
- wangp/llm_runtime.py -> configurable bundled/local runtime plus explicit external-provider fallback and fail-closed credential/provenance checks
- wangp/recovery.py -> OOM diagnosis and one-click style-preserving remediation plan (resolution, segment/window, offload, or profile change)
- wangp/remote.py -> explicit host access status and command preview through existing host configuration
- docs/first-run.md -> profiles, downloads, LLM fallback, OOM recovery, host access, and authorization boundary
- tests/test_first_run_platform.py -> real-process first-run platform coverage; no mocks
- datasets/runs/maestro-parity/WD-4d90/ -> authorized host profile and smoke-render evidence

CONSUMES:

## Required Outcomes
### no-GPU verifiable now
- Real CLI tests feed representative local inventory fixtures (including no accelerator) and produce honest profile recommendations with measured fields and explicit unknowns; doctor behavior remains unchanged.
- OOM evidence from a committed failure record maps to one actionable remediation command that preserves style/model choice and never changes a gate silently.
- Download state transitions are exercised over real temporary files without network: absent, checksum-mismatch, partial, paused, and complete states are typed and resumable only on explicit command.
- LLM runtime selection resolves local configuration, external fallback, and missing credentials with redacted diagnostics; no provider is contacted in the no-GPU test.
- Remote access renders a host command preview from explicit configuration and exits 3 before SSH when configuration is incomplete.

### requires an authorized host render
- One separately authorized host profile/probe plus one governed smoke render through the already-supported H3 lane proves the recommended profile and remote path with a real artifact.
- If an OOM occurs during that authorized run, the resulting diagnosis and one-click remediation must be recorded; a clean run records readiness evidence instead.

## Testing Requirements
- `uv run --frozen --extra dev pytest tests/test_first_run_platform.py -q`, real CLI/files/temp state and no mocks.
- Block network/provider commands by PATH in the no-GPU test and assert zero invocations while still proving typed unavailable states.
- Authorized host evidence requires operator approval, read-only profile/probe output, actual run bundle, hashes, and queue provenance.

## MANDATORY SKILLS
- pvg

## Delivery Requirements
- Developer must use `pvg story deliver`, paste real command output, and provide an AC table plus hashes for every produced artifact and read-only input.
- A GPU-dependent claim may be made only from a recorded run bundle with command, repository commit, model/asset provenance, queue record, exit status, output hashes, QC/gate evidence, and operator authorization for that run. A plan, prompt, unit test, or intention is not generation evidence.
- No story may silently download a model, contact a host, use a paid provider, or claim a capability the matrix marks unverified.
